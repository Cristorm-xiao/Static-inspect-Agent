# 架构与工程取舍

## 核心流程

`CLI → scan → rule_check → llm_analyze → report → baseline/output`

LangGraph 负责四个节点的状态传递；CLI 负责输入、配置、基线及输出格式。`rules.py` 每个未命中缓存的文件只解析一次 AST，同时产出规则结果、函数指标和同文件定义索引。详细流程图见 [v0.3 改动说明](improvements-2026-10-10.md)。

## 模型分析

`llm_runtime.py` 使用固定数量的异步 worker、按函数数与保守字节估算大小分批、预留逻辑调用和输入预算。SDK 保留最多 2 次重试，因此逻辑调用预算不等于传输尝试数或账单上限。

模型输出需要函数 ID、片段相对行号、原文证据、影响及建议。`llm_protocol.py` 做字段与源码匹配检查。模型可请求同文件、唯一、实际被直接调用过的顶层函数定义，最多 4 项，一轮补查。查找不执行目标代码，不接受模型提供的路径，不读取任意磁盘文件。当前不支持跨文件或动态调用解析。

证据匹配不能证明结论正确。LLM 只提供待复核建议，不参与规则退出码或 SARIF。失败、截断、预算跳过等状态单独记录，不能等同于没有问题。

## 缓存与基线

源码缓存按内容、路径、版本和配置复用；模型结果按函数、同文件上下文、模型端点、提示词和配置复用。默认 TTL 为 24 小时，支持禁用或刷新。缓存可能包含源码，应按项目源码管理。损坏缓存重新计算，写入失败降级继续。模型别名变化需要人工刷新。

v2 基线按规则、路径、作用域和相关 AST 结构指纹匹配，保留重复数量。注释与行号变化不改变结构指纹；路径、作用域或相关结构变化仍可能重新报告。v1 基线保留行号匹配行为，可重新生成升级。

## 输出与错误码

Markdown 面向阅读，JSON 提供 findings 和 scan_stats / llm_stats / llm_outcomes，SARIF 2.1.0 只包含规则。退出码 0 为没有新规则发现，1 为有规则发现，2 为输入、配置、基线或输出错误。严格 LLM 完成门禁需要额外检查状态。

## 当前边界

- 支持 Python，不扫描依赖漏洞，不进行跨文件数据流分析。
- 名称绑定分析不等同于流敏感别名分析；条件赋值、动态全局修改等仍可能误判。
- 筛选与复杂度阈值是启发式，不能保证找到所有语义问题。
- 上下文工具范围有限，输出一致性、修复收益和人工采纳率尚未得到大规模验证。
- 新版质量和性能证据见 [改进验证报告](validation/2026-10-10-improvements.md)，旧报告保留历史结论。
