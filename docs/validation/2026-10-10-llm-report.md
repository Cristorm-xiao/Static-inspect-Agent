# 真实 LLM 分析验证补充报告

本文记录 v0.2 的历史行为。v0.3 已更换候选筛选和证据协议，后续结果见 [改进验证报告](2026-10-10-improvements.md)。

日期：2026-10-10（Asia/Shanghai）。本报告补充 [离线规则验证报告](2026-10-09-report.md)。原有产品源码、提示词及 `.env` 配置未因测评改变。

## 结论

真实 DeepSeek 调用、结果解析及 CLI 集成链路已跑通。**10/10 次正式请求成功，25 个真实函数产生 63 条建议**。逐条源码复核分为 **13 条具体改进线索、36 条低优先级或设计取舍建议、14 条描述不准确或上下文不足的建议**。没有确认新的生产 Bug；这组结果支持将当前 LLM 功能定位为需要复核的代码审查助手。

源码复核由 Codex 完成，分类具有判断成分，尚无独立人工真值。不能将 13/63 写成模型准确率，也不能把 63 条建议写成 63 个缺陷。同一函数的多个建议可能重叠，13 条不是 13 个独立问题。

## 1. 方法与调用边界

- 沿用 Requests、Flask、Click、HTTPX、Django 的原固定 commit。从 1,144 个跨度至少 30 行的候选函数中，按 `SHA256("20261010|项目:相对路径:行号:函数名")` 排序，每项目选前 5 个，合计 25 个。源片段、commit、行号及 SHA-256 均保留在 `samples.json`。
- 样本占候选总数约 2.19%，每项目等量抽取，不按项目规模加权，不代表整个项目质量。未将 965 个文件全部发给模型。
- 使用产品原 `_analyze_all`、提示词和解析器；每批 5 个函数，temperature=0.3、timeout=30 秒、SDK max_retries=2，没有追加 JSON schema 或输出 token 参数。
- 5 个真实项目批次顺序执行；同组 Requests 额外重复 2 次；8 个预先固定标签的合成对照分 2 批；单文件 CLI 集成再调用 1 次，共 10 次正式调用。对照组内部仍采用产品原有 gather 行为。
- 配置请求模型为 `deepseek-chat`，10 次实际返回均为 `deepseek-flash`。记录的是返回模型标识，不保证供应商以后保持相同模型版本。
- 正式测评前另有一次连通性探测，输入 7、输出 1 token，未计入下表。模型列表查询不计为分析调用。
- SDK 观察层记录请求内容、响应、耗时、usage 和 HTTP 尝试数，不改变请求参数；不保存密钥、请求头或推理正文。目标源码只读取，不导入或执行。

## 3. 全部 63 条建议的源码复核

| 类别 | 数量 | 含义 |
|---|---:|---|
| A：具体改进线索 | 13 | 有源码依据，可进入进一步审查；未实施重构或验证收益 |
| B：低优先级或设计取舍 | 36 | 风格偏好、公开 API、协议常量或需要兼容性权衡 |
| C：不准确或上下文不足 | 14 | 误读片段、跨片段混淆或证据不足以支持结论 |

完整记录：[source-review.csv](../../benchmarks/results/2026-10-10-llm/source-review.csv)、[source-review.json](../../benchmarks/results/2026-10-10-llm/source-review.json)。每条绑定原始调用、响应序号、源码链接和哈希。A 类也可能只有部分理由成立，详见逐条说明。

具体例子：

- Requests `_implementation` 中两个平台分支执行相同语句；`get_unicode_from_response` 中列表追加后未读取，是可核查的改进线索。但后者模型同时提出的异常逻辑问题未获确认。
- Django `create_renamed_fields` 的循环和条件层级确实较多，适合进一步审查；是否重构仍需考虑迁移逻辑语义和回归测试。
- Requests `build_connection_pool_key_attributes` 主要是长文档，实际只委托一次辅助调用。模型仍给出“职责过多”，暴露以文档长度筛选候选的噪声。
- Click `invoke` 的命名建议引用了另一输入函数中的 `dt`，属于跨片段混淆。
- HTTP 头、GET/HEAD、Python 平台标识经常被列为“魔法值”，通常缺少实际修改价值。

因此，当前提示词更擅长生成一般性维护建议；还缺少业务上下文、证据约束、优先级和去重机制。

## 4. 对照组与重复运行

8 个合成函数在调用前固定标签，4 个包含刻意设置的命名、重复、嵌套或魔法数字问题，4 个预期无需重点修改。函数均满足产品的 30 行门槛；部分反例通过文档长度达到门槛，专门观察该筛选策略。

- **4/4 个正例收到对应目标类型建议**。
- **4/4 个负例也收到建议**，包括“文档过长”、把合理的非负截断视为未解释的魔法数字等。
- 合计 12 条建议。这是小型定向对照，不是随机基准；标签含风格判断，不能外推准确率、召回率或总体误报率。

见 [control-outcomes.json](../../benchmarks/results/2026-10-10-llm/control-outcomes.json) 及预先保存的 `control-labels.json`。

Requests 同一批 5 个函数三次得到 **10、5、11 条建议**，三次均覆盖全部 5 个函数。按文件、行号、smell、reason 完全相等计算，两两集合交并比均为 0；这主要说明具体文字与条目会变化，**不等于语义一致性为 0**。本轮未制作独立语义匹配标注，不给出语义稳定率。

## 5. CLI 集成与适用限制

对 Requests 原始 `cookies.py` 副本执行 `main.main([目录, "--format", "json"])`：扫描 1 个文件，发送 1 个候选函数，返回 2 条 LLM 建议、0 条规则告警、退出码 0。验证了扫描 → 规则 → LLM → JSON 报告的连接。调用在已有 Python 进程内执行，2.448 秒不包含新进程启动，不与离线独立进程计时直接比较。

两条 CLI 建议针对默认常量与简单 bool 转换，属于待审查的维护建议。LLM 结果不影响退出码，符合产品现有设计。

尚未验证：大型项目全量 LLM 并发、限流恢复、长期服务可靠性、跨文件推理、修复后收益以及人工采纳率。原实现没有独立并发上限，Django 全量仍可能产生 178 批请求。当前结果不支持无人值守自动改代码或生产自动阻断。
